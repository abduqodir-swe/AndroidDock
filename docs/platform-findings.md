# AndroidDock: результаты проверки платформы

Дата обновления: 2026-10-09. Статус: технический прототип собран; выполнен аппаратный прогон POCO X7 Pro / Android 16. Непроверенные сценарии явно отмечены ниже.

## Предлагаемый объём прототипа

Один общий DockScreen с цифровыми часами, два хоста: MainActivity и DreamService. Сначала проверить ComposeView и его владельцев дерева внутри DreamService. Календарь и редактор не реализовывать до записи результатов этого этапа.

Эта проверка соответствует этапу 1 «Проверка платформы» в PLAN.md. Рекомендации ревью о первом техническом прототипе не создают дополнительного этапа и не меняют нумерацию плана.

## Аппаратный прогон 2026-10-09

- Проверяющий: Codex через ADB; владелец предоставил телефон и подтвердил установки.
- Версия APK: 0.0.1 (versionCode 1); implementation commit a4cd2c1, UI test
  933cb8a с проверкой пересоздания и ожиданием конца анимации поворота.
- Основной APK установлен. Первую установку тестового APK HyperOS отменил с
  INSTALL_FAILED_USER_RESTRICTED; после явного подтверждения владельцем установка
  и аппаратный тест прошли. Ни разрешения, ни защита установки не обходились.
- DreamService проверен через штатный «Посмотреть», а не через Activity или
  искусственную подмену зарядки. Команды `cmd dreams start-dreaming` на этой
  прошивке требуют root; приложение root не использует.
- Первые нажатия на отдельный thumb системного переключателя визуально меняли
  состояние, но screensaver_enabled оставался 0. Нажатие всей строки сохранило 1.
  Это особенность текущего UI-теста, не доказанный дефект AndroidDock или запрет HyperOS.
- Исходные параметры: screensaver_enabled=0, компонент Google Photos,
  activate_on_sleep=1, activate_on_dock=0; accelerometer_rotation=0,
  user_rotation=0, screen_off_timeout=600000 мс. Для поворота DreamService
  user_rotation временно менялся на 1 и был возвращён в 0.
- Первый замер простоя невалиден: MainActivity была за keyguard, передний план
  NotificationShade, активен системный MiuiDozeService. Этот прогон не доказывает
  отказ KEEP_SCREEN_ON и не заменяет тест автоматической заставки.
  Тайм-аут в его finally возвращён в 600000 мс.
- Повторный валидный замер: передний план MainActivity подтверждён до начала.
  При timeout 15000 мс через 20 секунд экран Awake и MainActivity по-прежнему
  на переднем плане. После KEYCODE_BACK передний план вернулся к Settings.
  Это подтверждает удержание экрана и выход Activity на этом устройстве.
- После ещё 22 секунд простоя на реальной зарядке активен MiuiDozeService,
  isPreview=false, canDoze=true; AndroidDock автоматически не запустился.
  screensaver_enabled=1, activate_on_sleep=1, mIsCharging=true, но PowerManager
  сообщает **mDreamsSupportedConfig=false**. Это конкретное ограничение текущей
  конфигурации прошивки. В [AOSP Android 16, canDreamLocked](https://android.googlesource.com/platform/frameworks/base/+/refs/heads/android16-release/services/core/java/com/android/server/power/PowerManagerService.java#3646)
  этот флаг является условием допуска обычных dreams; вывод согласуется с
  наблюдаемым поведением HyperOS, но не заменяет исследование её собственного исходного кода.
  Root, обход OEM-конфигурации и фоновый запуск Activity не реализованы.
- При Sleep из активного портретного предпросмотра AndroidDock DreamService
  завершился; после 2 секунд активен MiuiDozeService, keyguard showing=true,
  inputRestricted=true, secure=true. Логи подтверждают остановку и освобождение
  ресурсов. Для разблокировки владелец разрешил обычный свайп с настроенным
  доверенным Bluetooth-устройством; новых способов разблокировки приложение не добавляет.
- В конце прогона исходные системные настройки восстановлены: заставка выключена,
  выбран прежний Google Photos, activate_on_sleep=1, activate_on_dock=0,
  user_rotation=0, screen_off_timeout=600000 мс. Сам AndroidDock остаётся установленным.
- Док, Android API 26, другие OEM, увеличенный шрифт, настоящий жест Back,
  длительный расход энергии и переподключение питания отдельно не проверены.
  Проверка платформы дала положительный результат для ручного экрана и штатного
  предпросмотра и обнаружила ограничение автоматического запуска на этой прошивке.

## Проверки среды разработки 2026-10-09

- Созданы Git, Gradle Kotlin DSL, version catalog, :app и чистый Kotlin/JVM
  :core:model. Временный applicationId: dev.androiddock.prototype.
- Владелец согласовал для сборки прототипа minSdk 26, compileSdk/targetSdk 36.
  Окончательный выбор после аппаратных замеров остаётся открытым.
- JDK 17.0.20.1; Gradle 9.3.1; AGP 9.1.1; Kotlin 2.4.0; Compose BOM
  2026.03.00 (Compose UI 1.10.5), Coroutines 1.11.0, Activity 1.12.4,
  Lifecycle 2.10.0. Сборки шагов 1–3: `./gradlew assembleDebug test` успешны;
  тестовые исходники пока отсутствуют (`NO-SOURCE`).
- На шаге 5 добавлены 6 юнит-тестов ClockStateHolder (0 ошибок) и Compose UI test,
  прошедший на POCO. Turbine не требуется для этих проверок StateFlow; DataStore,
  сериализация, Room, DI, фоновые виджеты, CI и screenshot test framework не добавлены.
- Предупреждение SDK: парсер понимает XML до версии 3, установленный SDK
  содержит XML версии 4. Сборка проходит; обновление системного SDK не выполнялось.
- Compose UI 1.12.0 в официальном AAR требует minCompileSdk 37. Поэтому
  выбран стабильный BOM, совместимый с согласованным compileSdk 36; SDK
  не повышался молча. Источники:
  [Compose BOM](https://developer.android.com/develop/ui/compose/bom),
  [релизы Compose UI](https://developer.android.com/jetpack/androidx/releases/compose-ui),
  [AAR 1.12.0](https://dl.google.com/dl/android/maven2/androidx/compose/ui/ui-android/1.12.0/ui-android-1.12.0.aar).
- Первый запуск ADB в sandbox ограничен доступом к USB/локальному сокету.
  При разрешённом запуске вне sandbox ADB стартовал, но `adb devices -l`
  вернул пустой список. Это ограничение текущего подключения, а не результат
  тестирования DreamService на POCO или ограничение HyperOS.

Проверки среды сами по себе не заменяют аппаратный прогон; его данные приведены выше.

## Шаблон записи одного прогона

- Дата, проверяющий, версия приложения или commit: не заполнено.
- Устройство и производитель: не заполнено.
- Версия Android / API, версия прошивки / номер сборки: не заполнено.
- Реальное устройство или эмулятор: не заполнено; результаты эмулятора не заменяют проверку реального устройства.
- minSdk/targetSdk и версии проверяемых зависимостей: не выбраны.
- Тип зарядки/дока, настройки заставки, автоблокировки, ориентации и энергосбережения: не заполнено.
- Проверяемый хост и сценарий, точные шаги: не заполнено.
- Ожидаемое и фактическое поведение: не заполнено.
- Результат: не проверено / работает / ограничено / не работает.
- Логи или другие подтверждения: не приложены.
- Ограничения, найденное решение и необходимость повторной проверки: не заполнено.

Для каждого устройства и прошивки создавать отдельные записи; не переносить результат между производителями без проверки.

## Решения после прототипа

- Зафиксировать работоспособный способ размещения Compose в DreamService и управление жизненным циклом обоих хостов.
- Выбрать minSdk/targetSdk и записать обоснование в отдельный ADR; API 26+ пока только ориентир для minSdk.
- Зафиксировать различия производителей и поддерживаемые сценарии запуска и выхода.
- После получения результатов вернуться к календарю и редактору в рамках этапа 2.

Оконные захваты на этой прошивке иногда содержат чёрные области вместо
статического содержимого, вплоть до системной строки состояния. Семантические
проверки находят элементы. Владелец непосредственно подтвердил: часы, дата и
календарь на телефоне видны полностью. Это **наблюдение о неполных захватах**,
а не доказанный дефект отображения; причина не установлена. Такие изображения
не считаются подтверждением полноты интерфейса. Дополнительно сохранены захваты
самой Compose-поверхности отдельно от оконных снимков.

Первый расширенный UI-прогон выявил проблему объединения семантики корневого
жеста и упал. Корневой жест переведён на pointerInput; последующие четыре теста
прошли. История не заменяется удачным результатом:
[первый сбой](evidence/stage2-ui-test-initial-failed.txt),
[финальный UI-прогон](evidence/stage2-ui-test.txt).

Кнопка настроек заставки использует ACTION_DREAM_SETTINGS с CLEAR_TOP:
на HyperOS запуск без флага иногда возвращал верхнее старое окно Settings
(например, Wi-Fi), запуск с флагом открывает DreamSettingsActivity.

Системные font_scale, user_rotation, accelerometer_rotation и выбор заставки
после проверок восстановлены; приложение не изменяет их при обычной работе.
Значения до/после записаны в [прогоне устройства](evidence/stage2-device-checks-final.json).
Длительная работа ночью, расход энергии, термонагрузка, эффективность pixel-shift
против выгорания, минимальный API 26 и другие прошивки пока не проверены.

Дополнительный критерий этапа 2 выполнен на устройстве: через редактор выбран
портретный Solo, выполнены `am force-stop` и новый запуск Activity. Полная
сохранённая JSON-конфигурация до/после совпала, календарь отсутствует в Solo.
Затем исходный Duo возвращён через редактор:
[проверка перезапуска](evidence/stage2-process-restart.json).

Повторный захват Dream выполнен с проверкой фактической ориентации дисплея:
портрет 1220×2712, затем ландшафт 2712×1220. Оба кадра полные, один и тот же
Dream token сохраняется при повороте:
[портрет](evidence/stage2-dream-portrait.png),
[ландшафт](evidence/stage2-dream-landscape.png),
[размеры и состояние](evidence/stage2-dream-capture-check.json).
Ранний кадр, снятый до стабилизации поворота и ошибочно названный портретным,
не использовался как доказательство портрета; эти файлы заменены повторным
валидным захватом. Фото-фон и циферблаты имеют отдельные native Compose captures
в [stage2-captures](evidence/stage2-captures/); оконные снимки с неполными областями
